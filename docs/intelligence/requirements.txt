Intelligence & MLDeep Research + Product Requirements Document

First-class intelligence architecture across Money, Productivity, Learning, Maintenance, Fitness and future WholeSignal domains.

1. Product Thesis
WholeSignal Intelligence is the cross-domain layer that converts historical system-of-record data into increasingly higher levels of useful reasoning. The system must distinguish deterministic facts and projections from learned predictions, and learned predictions from recommendations and agent actions.
Naming correction.  This product is WholeSignal Intelligence. 'Maintenance' is only one downstream domain that can supply data to and receive intelligence from this layer.

Non-negotiable separation.  The LLM may explain a numeric prediction, but must not invent the number. The Prediction Engine returns structured values, uncertainty, version and evidence metadata; the agent consumes that contract.

4. Problem Framing Contract
Every predictive feature must define: user outcome, target/label, prediction horizon, eligible population, feature cutoff time, baseline, evaluation metric, product success metric and failure/safety behavior.
If the future outcome cannot later be observed reliably, classify the feature as analytics/recommendation—not supervised prediction.
Start with simple baselines and only increase model complexity when held-out temporal performance demonstrates value.

8. Point-in-Time Correctness & Leakage Prevention
A training row may only use data whose event/source timestamp was available at the prediction cutoff.
Store feature snapshots for materially important predictions or enough lineage to reproduce them.
Separate eventTime (when reality occurred) from recordedAt (when WholeSignal learned it).
Prevent label leakage from completion status, post-outcome notes, future balances or later-edited metadata.
For time-dependent evaluation, use chronological holdout and/or time-series cross-validation with an optional gap.

Gate
Behavior
No history
Show analytics/projection only; explain what data would enable prediction.
Insufficient history
Keep candidate in shadow/readiness mode; no user-facing probability.
Sparse label coverage

Low temporal stability
Prefer baseline or suppress prediction.
Model below baseline
Do not deploy.
Poor calibration/coverage
Do not expose probability/range as trustworthy.
Stale model/data
Display stale state and use deterministic fallback if possible.

10. Evaluation & Uncertainty
Prediction type
Examples of evaluation
Regression
MAE/RMSE; interval coverage/width; error by horizon.
Probability/classification
Log loss/Brier; ROC/PR where appropriate; calibration/reliability.
Forecast
Temporal backtest; MAE/MASE/MAPE only where mathematically suitable; prediction interval coverage.
Anomaly
Precision from reviewed anomalies; alert burden; false-positive rate.
Duration
Median absolute error; under/over-estimation asymmetry.

Avoid a universal accuracy score.  A ₹ expense forecast, 0/1 task prediction and anomaly detector cannot be meaningfully collapsed into one percentage. The UI should show domain-specific performance and plain-language reliability.

14. Explainability
Show 'why this prediction' using interpretable feature contributions or rule explanations appropriate to the model.
Never present feature importance as causation.
Show model/data freshness, prediction horizon and uncertainty.
Provide 'What would change this?' scenario controls where deterministic simulation is valid.
If explanation quality is weak, say so rather than fabricate a narrative.
15. Privacy, Consent & Safety
Intelligence is opt-in by data domain/purpose where practical; disabling intelligence does not delete core system-of-record data unless user requests deletion.
Minimize feature copies of sensitive source data; prefer derived numeric/categorical features with lineage.
Do not use private health, relationship or location data for unrelated predictions without explicit scope.
No disease diagnosis, mental-health inference, pregnancy inference, criminality, sexuality or similarly sensitive personal-trait inference.
Predictions must never automatically trigger consequential financial, medical, employment or relationship actions.
Support export, deletion, consent revocation and audit trail for model-generated records.

17. MLOps Architecture
Recommended evolution: WholeSignal domain services emit events → analytical store/feature pipeline builds point-in-time datasets → Python training jobs create candidate models → registry stores versions/lineage → prediction service serves champion models → Prediction records are written back through the Intelligence service → Agent calls Intelligence tools.
Do not create infrastructure prematurely.  A dedicated feature store or heavyweight orchestration platform is optional until scale requires it. The interfaces should be feature-store-compatible, but V1 can use versioned SQL/Python feature pipelines over PostgreSQL/analytics storage.

19. Cross-Domain Intelligence
Begin with descriptive cross-domain correlations and user-controlled comparisons.
Only create predictive cross-domain models after sufficient data, explicit consent and demonstrated lift over single-domain baselines.
Avoid statements like 'sleep causes productivity'. Prefer 'In your recorded data, task completion was higher on days with X; this is an association, not proof of cause.'

21. Non-Functional Requirements
NFR-01  Deterministic projections reproducible for identical inputs/version.
NFR-02  Prediction inference must never mutate domain state.
NFR-03  Model and feature versions included in prediction lineage.
NFR-04  Sensitive free text excluded from model features unless explicitly approved.
NFR-05  All prediction timestamps timezone-safe; UTC storage + user-local display.
NFR-06  Offline app shows cached predictions with freshness labels; no fabricated recomputation.
NFR-07  Accessibility: confidence/state conveyed by text, not color only.
NFR-08  Deletion requests propagate to derived intelligence artifacts per policy.
NFR-09  Observability separates model errors from missing-data/readiness states.

24. Key Failure Modes
Failure
Required response
Too little data
Do not predict; show readiness and deterministic alternative.
Leakage discovered
Disable affected version; rebuild dataset; mark historical metrics invalid.
Model degrades
Fall back to baseline/previous champion.
Feature unavailable
Return unavailable/partial state, not a made-up value.
Outcome delayed
Keep unresolved; do not score prematurely.
Prediction conflicts with hard rule
Hard deterministic constraint wins.
Agent paraphrase changes numeric meaning
UI renders structured prediction card; LLM text is secondary.
