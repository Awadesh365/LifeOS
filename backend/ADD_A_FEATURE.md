# Add a Feature — Quick-Card

> The mechanical loop you repeat for **every** new feature, in the architecture from [`BACKEND_BLUEPRINT.md`](./BACKEND_BLUEPRINT.md).
> This card is the "what to type"; the blueprint is the "why". When in doubt, open the blueprint part noted on each step.

---

## TL;DR — scaffold all 5 files at once

From your **backend root**:

```bash
node scripts/scaffold-feature.js <feature> [surface]

# examples
node scripts/scaffold-feature.js orders            # surface defaults to main-cms
node scripts/scaffold-feature.js vehicleBrands main-cms
```

The script creates the five files below (skipping any that already exist) and prints the one line you add to `src/app.js`. Then you just fill in the `TODO`s.

> Prefer to do it by hand? Follow the 6 steps — they're the same order the script writes the files.

---

## Step 0 — data model & migration (only if the feature needs a new table)

Do this **before** the 6 steps, because your service (Step 2) imports the model. This step is intentionally **not** generated by the scaffold script — schema is too important to autopilot. Three things: write the model, register it, write the migration.

> Conventions baked in (from this repo): UUID primary keys, a `tenant_id` foreign key for tenant isolation, a soft-delete trio (`deleted` / `deleted_at` / `deleted_by`), `created_by` / `updated_by` audit columns, `underscored` snake_case columns with `created_at` / `updated_at` timestamps, and **partial indexes** on the columns you filter by. → *Blueprint Parts 4.2–4.4, 6*

### 0a. The model — `models/<surface>/<feature-singular>.js`

Models are named **singular** (`order.js` → class `Order` → table `orders`).

```js
// models/main-cms/order.js
// CONCEPT: typed table mapping with tenant isolation, soft delete, and hot-path indexes.
const { Model } = require('sequelize');

module.exports = (sequelize, DataTypes) => {
  class Order extends Model {}

  Order.init(
    {
      id: { type: DataTypes.UUID, primaryKey: true, defaultValue: DataTypes.UUIDV4 },
      tenant_id: {
        type: DataTypes.UUID,
        allowNull: false,
        references: { model: 'tenants', key: 'id' },   // tenant isolation
      },

      // TODO: your domain columns
      customer_id: {
        type: DataTypes.UUID,
        allowNull: false,
        references: { model: 'customers', key: 'id' },
      },
      status: {
        type: DataTypes.ENUM('PENDING', 'PAID', 'CANCELLED'),
        allowNull: false,
        defaultValue: 'PENDING',
      },
      amount: { type: DataTypes.DECIMAL(12, 2), allowNull: false },

      // soft-delete + audit trail (repo convention)
      deleted: { type: DataTypes.BOOLEAN, allowNull: false, defaultValue: false },
      deleted_at: { type: DataTypes.DATE, allowNull: true },
      deleted_by: { type: DataTypes.UUID, allowNull: true },
      created_by: { type: DataTypes.UUID, allowNull: true },
      updated_by: { type: DataTypes.UUID, allowNull: true },
    },
    {
      sequelize,
      tableName: 'orders',
      underscored: true,
      timestamps: true,
      createdAt: 'created_at',
      updatedAt: 'updated_at',
      // CONCEPT: partial indexes — only index live rows you actually query.
      indexes: [
        { fields: ['tenant_id', 'status'], where: { deleted: false } },
        { fields: ['tenant_id', 'customer_id'], where: { deleted: false } },
      ],
    },
  );

  return Order;
};
```

### 0b. Register it in `models/index.js`

```js
// 1) instantiate it alongside the other models
const Order = require('./main-cms/order')(sequelize, DataTypes);

// 2) declare associations in the associations block
Order.belongsTo(Tenant, { foreignKey: 'tenant_id' });
Order.belongsTo(Customer, { foreignKey: 'customer_id' });

// 3) make sure Order is included in the exported `models` object
//    so services can call models.Order
```

Then set the `MODEL` line the scaffold left as a TODO in your service: `const MODEL = models.Order;`.

### 0c. The migration — `scripts/migrations/<timestamp>-create-orders.js`

Name it with a sortable timestamp prefix (e.g. `20260622101500-create-orders.js`).

```js
'use strict';
// CONCEPT: schema change as a versioned, replayable migration (Blueprint Part 4.3).
// Runs via `npm run db:migrate` on the DIRECT db url (bypasses PgBouncer).
module.exports = {
  async up(queryInterface, Sequelize) {
    // Idempotent guard — safe to re-run (repo convention).
    const [rows] = await queryInterface.sequelize.query(
      "SELECT EXISTS (SELECT 1 FROM information_schema.tables WHERE table_name = 'orders') AS exists;",
    );
    if (rows[0]?.exists) return;

    await queryInterface.createTable('orders', {
      id: { type: Sequelize.UUID, primaryKey: true, defaultValue: Sequelize.UUIDV4 },
      tenant_id: { type: Sequelize.UUID, allowNull: false, references: { model: 'tenants', key: 'id' } },
      customer_id: { type: Sequelize.UUID, allowNull: false },
      status: { type: Sequelize.ENUM('PENDING', 'PAID', 'CANCELLED'), allowNull: false, defaultValue: 'PENDING' },
      amount: { type: Sequelize.DECIMAL(12, 2), allowNull: false },
      deleted: { type: Sequelize.BOOLEAN, allowNull: false, defaultValue: false },
      deleted_at: { type: Sequelize.DATE, allowNull: true },
      deleted_by: { type: Sequelize.UUID, allowNull: true },
      created_by: { type: Sequelize.UUID, allowNull: true },
      updated_by: { type: Sequelize.UUID, allowNull: true },
      created_at: { type: Sequelize.DATE, allowNull: false, defaultValue: Sequelize.NOW },
      updated_at: { type: Sequelize.DATE, allowNull: false, defaultValue: Sequelize.NOW },
    });

    await queryInterface.addIndex('orders', ['tenant_id', 'status']);
  },

  async down(queryInterface) {
    await queryInterface.dropTable('orders');
  },
};
```

Apply it: `npm run db:migrate`. Now the model exists and you can run the 6 steps.

## The 6 steps (build bottom-up)

### 1. Schema — the input contract
`schemas/<surface>/<feature>.schemas.js`

Define what valid `body` / `query` / `params` look like. Unknown fields are rejected by default.
**Why:** validate at the boundary; never trust the client. → *Blueprint Part 5*

### 2. Service — the business logic
`services/<surface>/<feature>/<feature>.service.js`

The only layer that knows your domain. Scope every query by `tenantId`, wrap multi-step writes in a `sequelize.transaction`, throw typed errors (`err.status`, `err.code`), and push heavy/non-critical work to a queue instead of doing it inline.
**Why:** it stays HTTP-free, so workers, cron, and tests reuse the exact same logic. → *Blueprint Parts 2.4, 4.2, 11*

### 3. Core controller — the HTTP glue
`controllers/core_controllers/<surface>/<feature>/<feature>.controller.js`

Read values off `req`, build a clean args object, call the service, set the status code, `return next(err)` in the catch. **No DB calls, no business rules here.**
**Why:** keeps transport details out of your domain. → *Blueprint Part 2.3*

### 4. API controller — the public surface (facade)
`controllers/api_controllers/<surface>/<feature>/<feature>.api.controller.js`

Re-export **only** the actions this surface (admin CMS / customer app / partner API) is allowed to call.
**Why:** explicit, minimal exposure — you can't accidentally leak an admin action to the public app. → *Blueprint Part 2.2*

### 5. Route — the pipeline
`routes/api_routes/<surface>/<feature>.routes.js`

Declare each endpoint with middleware **in this order**:

```
authMiddleware → authorize('<module>', '<action>') → validate({ schema }) → handler
```

**Why:** security and validation are uniform and visible, not buried in handlers. → *Blueprint Parts 2.1, 6, 7*

### 6. Register the route (the step everyone forgets)
In `src/app.js`:

```js
const ordersRoutes = require('../routes/api_routes/main-cms/orders.routes');
app.use('/api/main-cms', ordersRoutes);
```

Until you do this, the endpoint returns 404 no matter how perfect the other four files are.

## Before you call it done

- **Test it:** a unit test on the service + an integration test on the route. → *Blueprint Part 16*
- **Offload slow work:** if the feature sends an email / builds a report / pushes a notification, enqueue it to a worker rather than blocking the response. → *Blueprint Part 11*
- **Flag the optional:** gate any non-critical part behind a feature flag so it can be turned off under load. → *Blueprint Part 12*
- **Index your filters:** add a DB index for every column you filter or join on, and paginate every list. → *Blueprint Part 4.4*

---

## What each layer must NOT do (keeps the architecture clean)

| Layer | Does | Must **not** |
|---|---|---|
| **route** | declare URL + middleware pipeline | contain any logic |
| **api controller** | re-export allowed actions | reshape data or call services directly |
| **core controller** | read `req`, shape the response, `next(err)` | touch the DB or hold business rules |
| **service** | business logic, transactions, tenant scoping | know about `req`/`res`/HTTP |
| **schema** | declare & validate input | run side effects |

If you ever feel like breaking one of these rules, that's the signal the logic belongs in a different layer.

## Layout note

This architecture groups code as `<surface>/<feature>` — e.g. the `orders` feature on the `main-cms` surface lives at:

```
routes/api_routes/main-cms/orders.routes.js
controllers/api_controllers/main-cms/orders/orders.api.controller.js
controllers/core_controllers/main-cms/orders/orders.controller.js
services/main-cms/orders/orders.service.js
schemas/main-cms/orders.schemas.js
```

A **surface** is an API audience (`main-cms`, `customerApp`, `hubApp`, `directApp`, partner `integrations`). The same service can be reused behind multiple surfaces — that's the whole point of the thin api-controller facade. Pick one layout convention per project and keep it consistent.
